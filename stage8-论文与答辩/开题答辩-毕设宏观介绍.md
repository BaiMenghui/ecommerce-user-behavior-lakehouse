# 基于湖仓一体架构的电商用户行为数据分析平台 —— 开题答辩介绍

> 本文档从宏观视角介绍毕业设计的选题动机、研究内容、技术路线、预期成果与可行性，供开题答辩使用。

---

## 一、选题背景与意义

### 1.1 背景：行为数据爆炸与传统架构的矛盾

电商平台每天产生海量用户行为数据（浏览、收藏、加购、购买）。这些数据是理解用户、优化商品运营、支撑业务决策的核心资产。然而在实践中，传统数据处理架构暴露出两个突出问题：

- **传统数据仓库（Hive/关系型数仓）**：擅长结构化数据的批量分析与 SQL 加工，但 schema 约束严格、不支持高效的数据更新与事务，面对"边写入边修正、多场景消费"的现代数据需求显得僵化；
- **纯数据湖（HDFS 上直接存文件）**：存储灵活、成本低的，但缺乏事务、主键管理和 schema 治理，容易退化为"数据沼泽"。

**湖仓一体（Lakehouse）** 架构应运而生：以 Apache Hudi、Iceberg、Delta Lake 为代表的开放表格式，在数据湖存储之上补齐了事务、upsert、时间旅行、增量消费等仓库级能力，成为当前大数据领域的主流演进方向，也是各大厂实时数仓与离线数仓统一化的技术底座。

### 1.2 意义

**工程实践意义**：本项目以真实电商行为数据为对象，完整落地"清洗 → 入湖 → 分层建模 → 指标计算 → 服务化 → 可视化"的现代数据链路，是对湖仓一体架构的一次端到端工程验证。

**学习与研究意义**：数据平台开发涉及存储格式选型、数仓建模方法论、数据质量治理、服务化设计、前端可视化等多个知识域，本课题将它们串联为一个整体，训练的是**全链路系统思维**——这正是数据工程岗位的核心能力模型。

**应用价值**：平台产出的 DAU、GMV、转化漏斗、热销榜、时段热力等指标，直接对应电商运营的日常决策场景，具备真实业务价值，而非"为了技术而技术"。

## 二、国内外研究与技术现状

| 阶段 | 代表技术 | 特点与局限 |
|---|---|---|
| 传统数仓 | Oracle / MySQL / Hive | SQL 生态成熟、分析能力强；但更新代价高、扩展性受限 |
| 大数据平台 | Hadoop + Hive + Spark | 分布式批处理成熟；但时延高、无事务、更新困难 |
| 数据湖 | HDFS + Parquet + Spark | 存算分离、成本低；但无主键、无事务，治理困难 |
| **湖仓一体** | **Hudi / Iceberg / Delta Lake** | **在湖存储上提供 ACID 事务、upsert、增量读取、时间旅行** |

其中 Apache Hudi 由 Uber 开源，特色是**记录级 upsert 与增量消费**，特别适合"行为数据不断追加 + 偶发修正"的场景，因此本课题选择 Hudi 作为湖仓表格式。

在应用层，业界普遍采用 **Kimball 维度建模**（ODS→DWD→DWS→ADS 分层）组织数仓，配合"分层校验、口径对账"保障数据质量；在消费端，REST API + 前端可视化大屏是指标服务的标准形态。本课题在每一环都采用业界主流方案，保证技术路线不过时、不偏门。

## 三、研究目标与内容

### 3.1 总体目标

构建一套**端到端、可复现、带质量保障体系**的电商用户行为湖仓分析平台：输入约 105 万条原始行为数据，最终在一块可视化大屏上输出可信的运营指标，且全链路支持一键重跑、结果逐位一致。

### 3.2 六阶段研究内容（宏观描述）

1. **数据清洗与预处理**：对原始行为数据执行缺失值、去重、异常过滤、时间标准化，按日期分区落盘，产出清洗报告——解决"数据从不可信到可用"的问题；
2. **湖仓入湖（ODS 层）**：基于 Spark + Hudi 构建 MOR 贴源表，获得事务与 upsert 能力——解决"文件变受管数据资产"的问题；
3. **数仓分层建模（DIM/DWD/DWS）**：按维度建模方法构建用户/商品/日期三张维度表、行为明细事实表和三张主题汇总宽表，并设计"三角核对"对账机制——解决"数据可分析、口径可对账"的问题；
4. **指标计算（ADS 层）**：面向应用计算 DAU、GMV、转化漏斗、热销 TopN、类目占比、时段热力五组指标，并建立 21 项多口径交叉校验——解决"指标可信"的问题；
5. **服务化（API 层）**：SpringBoot 封装 REST 接口，多级缓存（Redis/Caffeine 自动降级）——解决"指标可消费、演示可脱集群"的问题；
6. **可视化大屏**：Vue 3 + ECharts 构建七面板数据大屏，支持日期联动——解决"指标可读"的问题。

### 3.3 量化目标

- 数据规模：1,048,576 条行为记录，25 个日期分区
- 数据模型：10 张湖仓表（1 ODS + 3 DIM + 1 DWD + 3 DWS + 5 ADS 中的有效拆分组合）
- 质量闸门：六道（清洗四项校验 / 入湖分区校验 / 分区三角核对 / 21 项交叉校验 / 接口冒烟 / 大屏验收）
- 核心指标基线（示例日）：DAU 9,522、订单 2,510、GMV 695,041、客单价 402.46

## 四、总体设计与技术路线

### 4.1 系统架构（四层）

```
┌─────────────────────────────────────────────┐
│  展现层  Vue3 + ECharts 数据大屏（7 面板）      │
├─────────────────────────────────────────────┤
│  服务层  SpringBoot REST API + 多级缓存        │
├─────────────────────────────────────────────┤
│  计算层  Spark SQL（Hive Catalog）+ pandas     │
│          ODS → DIM/DWD/DWS → ADS 分层加工      │
├─────────────────────────────────────────────┤
│  存储层  Apache Hudi 湖仓（MOR/COW 混合选型）   │
└─────────────────────────────────────────────┘
```

### 4.2 技术选型

| 环节 | 选型 | 选择理由 |
|---|---|---|
| 清洗 | pandas | 单机数据量内存可承载，秒级清洗且便于产出细粒度质量报告 |
| 湖仓格式 | Apache Hudi 0.14.1 | 记录级 upsert、时间线事务、增量消费，行为数据修正场景契合度最高 |
| 计算引擎 | Spark 3.3 SQL | 数仓事实标准，Hive Catalog 兼容元数据管理 |
| 表格式混选 | ODS 用 MOR，DWS/ADS 用 COW | "写多读少用 MOR、读多写少用 COW"的代价权衡 |
| 服务 | SpringBoot + JDK17 | 生态成熟；CSV 内存索引实现零大数据集群依赖部署 |
| 可视化 | Vue3 + Vite + ECharts | 组件化开发效率高，图表类型覆盖大屏全部需求 |

### 4.3 数据流

原始 CSV → 清洗分区目录 → ODS 贴源表 → DIM/DWD/DWS 分层表 → ADS 指标表 → 结果 CSV → REST API → 大屏面板。每一跳都有明确的输入输出契约与校验闸门。

## 五、关键问题与解决思路

1. **数据质量如何保证？** 设计六道质量闸门贯穿全链路；对原始数据携带的异常日期分区（仅 16 条、游离主分析期 8 个月外），采取"清洗层忠实保留 + 服务边界口径收敛"的治理策略，兼顾数据血缘完整与消费口径正确。
2. **湖仓表格式如何选？** 不是一刀切：按读写比例混用 MOR/COW，并用分区校验与三角核对验证选型正确性。
3. **多指标口径如何一致？** DWD 作为唯一事实来源，DWS 收敛公共聚合，ADS 只做轻量加工；再用"明细 = Σ用户 = Σ商品 = Σ类目"的三角核对与 21 项交叉校验闭环。
4. **答辩/演示环境依赖重？** 服务层读 ADS 导出的 CSV 建内存索引，缓存自动降级，实现无 Hadoop 集群的轻量演示，同时不牺牲架构完整性。

## 六、预期成果

1. 一套可一键重跑的**六阶段湖仓分析平台**（脚本化、结果可复现）；
2. 一套覆盖清洗到消费的**六道数据质量闸门**体系（含对账报告）；
3. 一块**七面板可视化大屏**（KPI 卡、趋势、漏斗、Top10、类目占比、时段热力、行为分布）；
4. 一批可信的业务指标基线与完整的数据血缘文档。

## 七、可行性分析

- **技术可行**：全部采用业界主流开源组件（Hudi/Spark/SpringBoot/Vue），社区文档充足；单机 Spark local 模式 + 105 万行数据规模在个人电脑资源范围内即可完整运行；
- **数据可行**：数据集来自天池公开的淘宝 UserBehavior 数据集抽样，字段清晰、规模适中，具备真实业务语义；
- **能力可行**：前期已完成 Python/SQL/Java 及大数据组件的学习储备，且六阶段雏形已跑通，风险可控。

## 九、特色与创新点

1. **湖仓表格式混选实践**：在同一平台内按读写特征混用 MOR/COW，而非教条式单选，并给出选型依据与校验方法；
2. **全链路口径治理**：以"唯一事实来源 + 三角核对 + 多口径交叉校验"构成的质量闸门体系，让每个大屏数字都可回溯到明细；
3. **异常数据治理闭环**：从发现异常分区、保留血缘到服务边界收敛的完整故事，体现数据工程的真实决策过程；
4. **工程可复现性**：六阶段全脚本化、一键重跑、结果逐位一致，将"实验"提升为"工程"。
