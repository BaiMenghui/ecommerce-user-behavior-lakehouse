## 一、课题目标与可行性分析

### 1. 需求分析

电商平台的用户行为数据（浏览、收藏、加购、购买）是运营决策的核心依据。传统架构存在两类痛点：**数据仓库**（如 Hive）事务能力弱、增量更新困难、时效性差；**数据湖**成本低、格式灵活，但缺乏事务保障与统一管理，容易沦为"数据沼泽"。湖仓一体（Lakehouse）通过开放表格式在湖存储之上补齐 ACID 事务、增量查询与时间旅行能力，是当前业界明确的技术趋势。本课题的需求即：在学生可负担的单机环境下，构建一条**低成本、可复现、质量可证明**的电商用户行为湖仓分析链路，覆盖从原始日志到可视化大屏的完整闭环。

### 2. 达成目标

课题目标细化为四项可验收、可量化的指标：

1. **百万级行为记录入湖**：以阿里天池 UserBehavior 数据集 1,048,576 条真实行为记录为输入，按天分区写入 Hudi ODS 贴源表，完成行数、非空、日期三重校验；
2. **五层规范数仓体系**：构建 ODS → DIM → DWD → DWS → ADS 五层 Hudi 表体系，基于 Kimball 维度建模，各层 SQL 可独立重跑；
3. **四类业务指标体系**：DAU、GMV、转化漏斗、商品排行等指标统一口径，固化于 ADS 层，支撑可视化大屏；
4. **全链路一键复现**：全流程脚本化，任意阶段可重跑且结果与基准逐位一致。

### 3. 可行性分析

- **技术可行**：全栈选用业界主流开源组件（Hadoop 3.3 / Spark 3.3 / Hudi 0.14.1 / Kafka / SpringBoot / Vue3），文档充分、社区成熟；通过 Windows + WSL2 单机部署验证，普通笔记本即可承载百万级数据处理；
- **数据可行**：阿里天池 UserBehavior 为公开权威数据集，规模与字段满足电商行为分析全部场景，无数据获取成本与合规风险；
- **经济可行**：全组件开源，零授权成本，无需云资源租用；
- **进度可行**：按 12 周规划分阶段推进（环境→数据→入湖→建模→指标→服务→大屏→论文），每阶段有明确交付物与检查点，目前各阶段均已提前完成并通过验收。

## 二、算法原理

### 1. Kimball 维度建模四步法（数仓建模）

按"选择业务过程 → 声明粒度 → 确定维度 → 确定事实"四步建模：业务过程为用户行为事件；粒度声明为"一行 = 一个用户对一个商品的一次行为"；维度为 dim_user（用户）、dim_item（商品）、dim_date（日期）三类维度表；事实为行为次数、行为类型、时间间隔、会话序号。最终形成**星型模型**：dwd_user_behavior_fact 事实表居中，三张维度表环绕；会话（session）作为**退化维度**直接落入事实表。

### 2. 30 分钟超时会话切分算法（Spark 窗口函数）

以用户为单位按时间排序，用 `lag()` 窗口函数取同用户相邻两条行为的时间戳，计算间隔；若间隔超过 1800 秒（30 分钟，业界通行口径），则开新会话；会话内递增生成 session_seq。该算法在 DWD 层落地，还原用户连续行为路径，支撑漏斗与跳失分析。

### 3. Hudi MOR / COW 表格式原理（湖仓存储）

- **COW（Copy on Write）**：写入时重写底层 Parquet 文件，读侧零合并、查询快，代价是写放大；
- **MOR（Merge on Read）**：写入只追加 Delta Log，读时合并，写入快，代价是读放大；
- Hudi 以 **Timeline（时间线）** 管理所有 commit，基于时间戳实现**增量查询**（精确到 commit 级）与**时间旅行**。本课题按层读写特征混选：ODS/DWD 写多读少用 MOR，DIM/DWS/ADS 读多写少用 COW，并以对照实验验证。

### 4. 多口径数据质量校验算法

- **分区级三角核对**：同一明细事实分别按用户、商品、类目三个口径聚合，验证"明细数 = Σ用户 = Σ商品 = Σ类目"，四种行为类型分别对账；
- **21 项多口径交叉校验**：ADS 层与 DWD/DWS 层逐项互核（DAU/GMV/漏斗三层一致、新老用户守恒、TopN 排序与并列规则、占比合计≈100%、热力图合计=明细数等），任何一项不符即失败退出并打印差值。

### 5. 指标计算方法

转化漏斗（浏览→收藏→加购→购买四步及三段转化率）、Top-N 热销排行（按购买次数取 Top10，并列按 ID 升序）、新老用户占比（首活跃日期判定）、24 小时行为热力分布（event_time 派生小时字段聚合）。

## 三、课题实现过程、数据记录及处理

### 阶段 0：环境搭建

在 WSL2 中通过 docker-compose 编排 HDFS、Hive Metastore、Spark，集成 Hudi 0.14.1 Bundle；完成建表、写入、增量查询连通性验证；期间排查并修复 HMS 元数据不同步问题（编写 hms_resync 修复脚本）。记录：环境验证报告 1 份、验证脚本 9 个。

### 阶段 1：数据获取与预处理

数据源为阿里天池 UserBehavior 数据集，抽取 **1,048,576 条**行为记录（字段：user_id / item_id / category_id / behavior_type / ts）。pandas 八步清洗：总量基准建立 → 缺失值处理 → 业务主键去重（用户+商品+行为+时间戳）→ 异常过滤（行为类型限定 pv/fav/cart/buy）→ 时间戳转换（ts→event_time，派生 dt 分区字段）→ 按天落盘 → 生成清洗报告 → 自动校验。**数据记录**：产出 25 个有效日期分区；四项校验全 PASS；发现并标记异常分区 dt=2018-08-28（仅 16 条、游离主分析期 8 个月），采取"清洗层保留血缘、消费边界过滤"的治理策略。注：本项目以数据工程与统计分析为主，无模型训练环节。

### 阶段 2：数据采集入湖

Spark 批量读取 25 个清洗分区，写入 Hudi MOR 表 ods_user_behavior_log（主键 behavior_id 拼接生成天然防重，预合并字段 ts，按 dt 分区），采用"先清后灌"保证幂等。拓展完成 **Kafka + Structured Streaming 流式入湖**：producer 按 500 条/秒重放当日数据，微批 upsert 写入实时表，checkpoint 断点续传。**数据记录**：入湖 1,048,576 条；行为分布 pv 940,047 / cart 57,861 / fav 29,353 / buy 21,315；25 分区逐分区与清洗层一致；流式链路增量查询精确到 commit 级（第 3 个 commit 后增量 = 微批 4 的 13,951 条）。

### 阶段 3：湖仓分层建模

DIM 层：dim_user 20,404 条（代理键、首末活跃、生命周期分层）、dim_item 824,738 条、dim_date 25 条；DWD 层：dwd_user_behavior_fact 1,048,576 条（唯一事实来源，含会话切分与小时派生）；DWS 层（COW）：dws_user_action_day 73,544 / dws_item_action_day 711,458 / dws_category_action_day 32,326。**数据记录**：25 个分区逐分区三角核对（明细=Σ用户=Σ商品=Σ类目，四种行为分别对账）全部 PASS。

### 阶段 4：业务指标计算

构建 ADS 层 5 张指标表（COW）：ads_dau_trend / ads_funnel / ads_item_topn / ads_category_share / ads_hour_heatmap；执行 **21 项多口径交叉校验**全部 PASS；导出 5 份 CSV 供服务层消费（行数基准 24/24/154/32,317/284，已双保险过滤异常分区）。**数据记录**：基准日 2017-11-25：DAU 7,308、GMV 556,190、漏斗 99,250→2,921→6,010→2,043。

### 阶段 5：数据服务层

SpringBoot（JDK 17，端口 8080）读取 5 份 ADS CSV 构建内存索引，提供 8 个 RESTful 接口（统一 {code,msg,data} 响应）；Redis 优先、不可用时自动降级 Caffeine 并在健康检查如实上报。**数据记录**：8 接口冒烟全部 200，数值与 ADS 层逐位一致；大屏默认日 dt=2017-12-03 口径正确。

### 阶段 6：可视化大屏

Vue3 + ECharts 实现 4+2+1 布局大屏（Vite，端口 5173）：KPI 数字卡、DAU/GMV 双轴趋势、转化漏斗、Top10 排行、类目占比、24 小时流量、行为分布共 7 面板；切换日期并发拉取 6 个接口全面板联动。**数据记录**：浏览器实测验收通过，展示值与服务层冒烟值逐位一致。

### 全链路验证

六道质量闸门（清洗四项校验→入湖分区校验→三角核对→21 项交叉校验→接口冒烟→大屏验收）全部 PASS；全链路脚本化一键重跑，重跑结果与基准逐位一致。
