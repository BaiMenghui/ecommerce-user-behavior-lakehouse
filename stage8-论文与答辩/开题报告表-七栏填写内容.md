# 开题报告表 · 七栏填写内容
学生：白梦辉（20232102540）｜指导教师：包萨日娜｜课题：电商用户行为湖仓分析平台——基于 Apache Hudi 与 Spark 的湖仓一体全链路数据分析系统

## 一、课题来源及研究的目的和意义

**课题来源：** 自选课题。选题来源于电商平台海量用户行为数据"存得起、算得快、看得清"的现实需求与传统数据架构的固有矛盾。

**研究目的：** 基于 Apache Hudi 与 Spark 构建湖仓一体的电商用户行为分析平台，打通"数据源→采集入湖→分层建模→指标计算→数据服务→可视化大屏"全链路，在单机环境完成从原始日志到经营指标的端到端落地。

**研究意义：** ①技术意义：数据湖灵活廉价但缺乏事务保障，数据仓库事务强但时效与成本受限，本课题以 Hudi 的 ACID、增量读写与 COW/MOR 双存储模式验证"湖仓一体"替代"湖+仓"双链路的可行性；②工程意义：沉淀一套可复现的五层数仓建模范式（ODS/DIM/DWD/DWS/ADS）与标准化指标口径体系；③应用意义：支撑 DAU、GMV、转化漏斗、热销排行、活跃时段等核心经营指标的多维分析，为电商运营决策提供数据支撑；④个人意义：完整掌握大数据采集、存储、计算、服务、可视化全栈工程能力。

## 二、国内外在该方向的研究现状及分析

**国外：** 数据仓库理论自 Inmon（1991，CIF 架构）与 Kimball（维度建模、星型模型）确立以来长期主导企业分析场景；2011 年 James Dixon 提出数据湖概念，依托 Hadoop 生态解决半结构化数据存储问题，但存在无事务、脏数据堆积缺陷；为兼顾批处理与时效，Nathan Marz 提出 Lambda 架构、Jay Kreps 提出 Kappa 架构；2020 年 Databricks 正式提出 Lakehouse（湖仓一体）范式。Apache Hudi 起源于 Uber（2016，原名 Hoodie），2019 年成为 Apache 顶级项目，以 COW/MOR 双表格式、记录级 ACID 与增量查询成为湖仓一体核心组件；同类还有 Netflix 主导的 Iceberg 与 Databricks 的 Delta Lake。

**国内：** 腾讯、阿里、字节、美团等头部企业已在游戏、电商、风控场景大规模落地湖仓架构（如腾讯基于 Hudi 的游戏大数据平台、阿里 Flink+Paimon 流式湖仓生态）；国产开源社区活跃，Hudi 中文实践与文档日趋丰富；学界研究聚焦湖仓事务一致性、索引优化与批流一体。

**分析：** 湖仓一体已成为业界公认演进方向，但公开实践多基于大规模集群，面向教学与个人开发者的"单机轻量化湖仓全链路"完整案例仍然稀缺——本课题以此为切入点，兼顾完整性、可复现性与答辩可演示性。

## 三、主要研究内容

1. **湖仓环境搭建**：Docker Compose 编排 Postgres+Hive Metastore 元数据服务，WSL2 内以 pip 方式部署 Spark 3.3 + Hudi 0.14.1（本地文件系统仓库），完成建表、写入、更新、删除的冒烟验证；
2. **数据源准备**：选用阿里天池 UserBehavior 数据集（pv/fav/cart/buy 四类行为），取约 100 万条抽样子集（24 个有效活跃日，2017-09-11~12-03），完成探查、清洗与按日分区；
3. **数据采集入湖**：构建 ODS 贴源层 Hudi MOR 表，按 dt 分区、幂等 upsert 写入，配套入湖校验；
4. **五层分层建模**：遵循 Kimball 维度建模，构建 ODS→DIM（用户/商品/日期 3 张维表，COW）→DWD（行为事实表，MOR，含 30 分钟超时会话切分）→DWS（用户/商品/类目 3 张主题宽表，COW）→ADS 共 13 张表，并绘制数据血缘图谱；
5. **指标计算与 ADS 层**：计算 DAU、订单总量、GMV、客单价、三步转化漏斗、热销商品 Top10、类目占比、行为分布、活跃时段热力、新老用户占比等指标，产出 5 张面向大屏的 COW 扁平结果表；
6. **数据服务与可视化**：CSV 导出与 SpringBoot RESTful API + Redis 缓存双方案，Vue3+ECharts 大屏呈现 6 类视图；
7. **创新实验**：设计 Hive 分区表、Hudi COW、Hudi MOR 三组对照的存储模式性能对比实验；
8. **数据质量保障**：建立 DWD/DWS/ADS 多口径交叉校验体系。

## 四、研究方案

**总体技术路线：** 数据源→（清洗分区）→ODS 入湖→DIM/DWD/DWS 分层建模→ADS 指标计算→数据服务→可视化大屏，与五层 13 张表一一对应。

**技术选型及理由：** ①Hudi：记录级 ACID、增量查询、COW/MOR 双模式，是湖仓一体核心，且可与 Hive 基线做严格性能对照；②Spark 3.3：成熟稳定的批处理引擎，Spark SQL 完成建模与聚合；③Hive Metastore+Postgres：统一元数据管理；④服务层采用 SpringBoot+Redis 热点缓存，保留 CSV 静态导出降级方案；⑤前端 Vue3+ECharts；⑥Docker+WSL2 保证环境可复现、一键重建。

**数据与口径方案：** 清洗规则涵盖缺失值、重复值、时间戳转换与按日分区；因数据集无真实价格，GMV 采用确定性模拟单价口径（pmod(hash(item_id),450)+50 元）并在《指标口径文档》中显式声明，保证重跑与实验数据一致。

**关键方法：** Kimball 四步建模法；lag 窗口函数实现 30 分钟超时会话切分；幂等 upsert/insert_overwrite 写入；DWD↔DWS↔ADS 三方多口径三角校验。

**实验设计：** 固定硬件与数据量，设置 Hive 分区表（基线）、Hudi COW、Hudi MOR 三个对照组，选取用户行为统计、商品销售分析、分区增量查询、增量 Upsert 写入四类场景，控制变量、预热剔除冷启动、多轮取均值，以查询/写入耗时为评价指标，预期 Hudi 相对 Hive 查询耗时降低 30% 以上。

**可行性：** 阶段 0~6 已真实落地——12 张 Hudi 表共约 104.86 万行数据落湖，DWS/ADS 两级一致性校验全部通过，数据服务层 REST API 联调通过，Vue3+ECharts 可视化大屏已完成浏览器实测验收（8 接口联通、6 类视图渲染正常），证明技术路线切实可行。

## 七、研究过程中可能遇到的困难和问题、解决的措施

1. **湖仓组件版本兼容复杂**（Spark/Hudi/元数据服务间依赖敏感）：已通过冒烟测试提前暴露并解决（建表/写入/更新/删除全通过），以 Docker Compose 与版本锁定固化环境，故障可一键重建；
2. **数据口径争议**（数据集无真实价格、订单概念需近似）：坚持"口径文档先行"，模拟单价等口径显式声明并全局统一，配套多口径三角校验防止口径漂移；
3. **单机性能瓶颈**：采用 100 万条抽样子集、dt 分区裁剪、shuffle 参数调优；实验报告注明硬件环境，并说明完整数据集可通过集群横向扩展无缝支持；
4. **会话切分准确性**：以 15 项一致性校验与行为量守恒校验兜底，辅以抽样人工复核；
5. **服务层与前端工期风险**：主线先保证 CSV 静态数据方案可用，SpringBoot+Redis 接口与 Vue3 大屏按"最小可用"原则迭代，若时间不足按预案降级为静态页面/BI 工具；
6. **创新实验数据波动**：固定硬件与数据版本，预热剔除冷启动，多轮测试取均值以降低偶然误差。
