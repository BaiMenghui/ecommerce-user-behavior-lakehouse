# 电商用户行为湖仓分析平台 - 毕设详细时间规划与操作步骤

---

## 一、项目概述

**项目名称：** 电商用户行为湖仓分析平台

**核心技术栈：**
- **大数据存储基座：** Hadoop HDFS + Hudi + Hive Metastore
- **高性能计算引擎：** Apache Spark 3.x
- **高吞吐消息队列：** Kafka（加分项）
- **后端服务与缓存：** SpringBoot + Redis（加分项）
- **交互式数据可视化：** Vue3 + ECharts
- **标准化容器部署：** Docker

**版本信息：** Hadoop 3.3.x / Spark 3.4.x / Hudi 0.14.x

## 三、各阶段详细操作步骤

### 阶段 0：环境搭建（第 1-2 周）

**核心目标：** 搭建可运行的单机大数据环境，完成 Hadoop、Spark、Hive 与 Hudi 的组件集成，验证基础数据链路的通畅性。

#### 关键实施步骤

**步骤1：容器化底座构建**
- 安装 Docker Desktop 与 WSL2
- 配置容器网络与持久化存储卷
- 为集群提供隔离、轻量的运行环境

**步骤2：核心组件部署**
- 部署 Hadoop 分布式文件系统（HDFS）与资源调度（Yarn）
- 配置 Hive Metastore 作为元数据管理中心
- 确保各组件正常启动并可互相访问

**步骤3：集成与全链路验证**
- 部署 Spark 计算引擎并集成 Hudi Bundle
- 完成数据读写测试
- 完成增删改查功能验证
- 完成跨组件连通性测试

#### 阶段交付物
1. **环境编排文件** — docker-compose.yml 一键部署脚本，包含所有组件配置与启动命令
2. **环境验证报告** — 详细的组件连通性测试记录、服务状态截图及日志分析
3. **基础验证脚本** — 包含 Hudi 建表、数据写入与查询的自动化测试脚本

### 阶段 1：数据源准备（第 2 周）

**核心目标：** 锁定权威公开数据集，完成全维度数据探查与质量校验，统一字段口径与预处理规则。

#### 关键实施步骤

**步骤1：数据集获取**
- 选用阿里天池 UserBehavior 数据集（天池全量约 1 亿条交互记录；本课题取 100 万条抽样子集，时间跨度 2017-11-25 ~ 2017-12-03 共 9 天进行验证，与全阶段及论文口径统一）
- 数据集包含字段：用户ID、商品ID、类目ID、行为类型、时间戳等
- 行为类型覆盖：pv（浏览）、fav（收藏）、cart（加购）、buy（购买）

**步骤2：全量数据探查**
- 用户/商品规模统计
- 行为分布占比分析
- 数据质量检查（缺失值、重复值、异常值）
- 计算用户-商品交互矩阵稀疏度

**步骤3：标准化预处理**
- 缺失值填充
- 重复值剔除
- 时间戳转换（转换为标准日期时间格式）
- 按自然日完成数据分区与存储

#### 阶段交付物
1. **《数据集探查分析报告》** — 含质量指标与稀疏度分析
2. **清洗后数据文件** — 按日分区的结构化数据文件
3. **自动化数据清洗脚本** — 可复用的 Python 预处理脚本

---

### 阶段 2：数据采集入湖（第 3 周）

**核心目标：** 将清洗后的原始行为数据写入 Hudi ODS 层，完成数据入湖，验证增量写入能力。

#### ODS 层核心表设计
- **表名：** ods_user_behavior_log
- **类型：** Hudi MOR（Merge On Read）
- **分区：** 按 dt（天）分区
- **主键：** behavior_id
- **关键字段：** behavior_id, user_id, item_id, category_id, behavior_type, event_time, dt

#### 关键实施步骤

**步骤1：批量入湖**
- 使用 Spark 读取清洗后的数据
- 按天分区写入 Hudi MOR 表
- 配置 Hudi 表参数（主键、分区字段、预合并字段等）

**步骤2：入湖校验**
- 验证数据一致性（条数核对、字段核对）
- 验证分区完整性
- 查看 Hudi Timeline 确认提交记录
- 验证数据查询正确性

**步骤3（拓展/加分）：Kafka + Structured Streaming 准实时入湖**
- 部署 Kafka 消息队列
- 使用 Spark Structured Streaming 消费 Kafka 数据
- 实现准实时数据入湖

#### 阶段交付物
1. ODS 层建表 SQL 与 PySpark 脚本
2. 自动化数据入湖执行脚本
3. 数据完整性与一致性校验报告

---

### 阶段 3：湖仓分层建模（第 4-5 周）

**核心目标：** 基于Kimball维度建模理论，构建完整的湖仓分层体系，打通数据流转链路。

#### 分层架构

**第一层：DIM 维度层（基础主数据底座）**
- dim_user — 用户维度表
- dim_item — 商品维度表
- dim_date — 时间维度表
- 采用 Hudi COW 表存储，确保维度数据的一致性与高效更新

**第二层：DWD 明细层（原子化事实存储）**
- dwd_user_behavior_fact — 用户行为事实表
- 执行去重、异常过滤
- 会话划分（Session 切分）
- 维度退化
- 保留最细颗粒度数据，支持灵活的下钻分析

**第三层：DWS 汇总层（主题宽表聚合）**
- 按"实体×天"粒度聚合
- 用户主题宽表
- 商品主题宽表
- 类目主题宽表
- 大幅减少上层应用的计算量，提升查询性能

#### 关键实施步骤

**第4周：DWD + DIM 层构建**
1. 设计维度表结构与事实表结构
2. 编写 DIM 层 ETL 脚本（从 ODS 抽取维度数据）
3. 编写 DWD 层 ETL 脚本（数据清洗、会话划分、维度退化）
4. 测试与验证数据准确性

**第5周：DWS 层主题宽表构建**
1. 梳理业务主题与指标需求
2. 设计 DWS 层宽表结构
3. 编写 DWS 层聚合计算脚本
4. 梳理并绘制数据血缘关系图谱
5. 验证汇总数据与明细数据的一致性

#### 阶段交付物
1. DIM/DWD/DWS 各层建表 SQL 脚本
2. 各层 ETL 计算脚本
3. 数据血缘关系图谱
4. 数据一致性校验报告

### 阶段 4：业务指标计算（第 6-7 周）

**核心目标：** 基于 DWS 主题宽表计算电商全域核心业务指标，输出标准化 ADS 层结果表。

#### 指标体系

| 类别 | 必做指标 | 加分指标 |
|------|----------|----------|
| **整体运营 KPI** | DAU、订单总量、GMV、客单价 | MAU、用户留存率、全渠道复购率 |
| **转化漏斗分析** | 浏览→加购→购买三步转化率 | 浏览→收藏→加购→购买全链路漏斗 |
| **商品销售洞察** | 热销Top10商品、类目销售占比 | 商品复购率、新品动销率监测 |
| **用户画像分析** | 用户行为分布、新老用户占比 | RFM分层模型、流失预警分析 |
| **业务趋势研判** | 日GMV趋势、小时流量峰谷 | 周环比增长、月同比增长率 |

#### 关键实施步骤

**步骤1：定义指标口径**
- 编写标准化指标文档
- 明确每个指标的计算公式
- 明确统计粒度与时间范围
- 说明业务含义，确保数据一致性

**步骤2：创建 ADS 结果表**
- 设计 ADS 层宽表结构
- 用于存储最终聚合计算结果
- 优化表结构以适配大屏高并发查询需求

**步骤3：执行指标计算**
- 利用 Spark SQL 读取 DWS 层数据
- 按照预设口径进行聚合计算
- 将结果写入 ADS 表或导出为 CSV 文件

**步骤4：数据校验验证**
- 与原始明细数据汇总核对
- 多口径交叉验证
- 确保指标计算结果准确无误

#### 阶段交付物
1. 标准化指标口径文档
2. ADS 层建表脚本与计算脚本
3. 指标计算结果数据
4. 指标校验报告

### 阶段 5：数据服务层（第 8 周）

**核心目标：** 将 ADS 层计算好的指标封装为可被前端直接调用的服务接口。

#### 方案一：简化版（本科推荐）

**实现方式：**
- Spark 计算完成后，将结果直接导出为 CSV 或 JSON 文件
- 前端页面直接读取本地静态文件

**核心优势：**
- 开发量极小
- 无需搭建后端服务
- 环境配置简单
- 适合快速验证

**局限性：**
- 数据无法实时更新
- 无接口封装
- 扩展性较差

#### 方案二：完整版（答辩加分）

**实现方式：**
- 使用 SpringBoot 构建 RESTful API
- 引入 Redis 缓存高频查询结果
- 降低数据库压力

**核心优势：**
- 架构完整规范
- 高度贴近企业真实生产环境
- 是项目答辩的重要亮点

**挑战：**
- 需要具备 Java 开发基础
- 整体工作量和复杂度较高

#### 阶段交付物
- **简化版：** ADS层指标数据文件包（CSV/JSON格式）
- **完整版：** API接口文档、SpringBoot后端源码、Redis配置文件、接口测试报告

### 阶段 7：系统测试与创新实验（第 10-11 周）

**核心目标：** 完成全链路功能验收，并进行存储模式性能对比创新实验。

#### 全链路功能验收清单

| 测试项 | 测试内容 |
|--------|----------|
| **数据入湖验证** | 批量写入Hudi ODS表，验证数据完整性、分区正确性及无乱码丢失 |
| **数仓分层计算** | 校验DWD/DIM/DWS/ADS层级逻辑，确保指标口径一致，计算结果准确 |
| **多维查询验证** | 覆盖快照查询与增量查询场景，验证Hive/Spark查询结果无报错 |
| **可视化大屏验收** | 端到端验证大屏加载速度、图表渲染效果及数据实时性展示 |

#### 核心创新：存储模式性能对比实验

**实验目标：**
针对电商典型查询场景，对比传统Hive方案与Hudi COW/MOR模式在查询耗时与吞吐量上的差异，验证湖仓一体架构的性能优势。

**实验设计：**
1. 选取典型电商查询场景（如用户行为统计、商品销售分析等）
2. 分别在传统Hive分区表、Hudi COW表、Hudi MOR表上执行相同查询
3. 记录查询耗时、吞吐量等指标
4. 进行多轮测试取平均值，确保结果可靠性

**预期成果：**
- Hudi MOR 结合索引优化方案
- 预计查询耗时降低 30% 以上
- 吞吐量提升显著
- 满足高并发实时分析需求

#### 阶段交付物
1. 系统功能测试报告
2. 性能对比实验报告（含数据图表）
3. 实验分析与结论

## 四、风险与降级方案

| 序号 | 风险描述 | 降级方案 |
|------|----------|----------|
| **01** | Hudi 部署与环境适配风险：部署失败、环境依赖复杂导致调试周期长 | 改用 Hive 分区表实现数据分层，Hudi 作为技术预研与后续优化的对比实验 |
| **02** | 全量数据处理性能瓶颈：单机 Spark 无法承载全量数据计算，任务崩溃 | 采用 100 万条数据抽样子集验证（与全阶段统一口径一致），文档说明完整数据集可通过集群扩展无缝支持 |
| **03** | 后端开发人力与能力缺口：微服务架构开发难度大，人力投入不足 | 简化服务层设计，采用 CSV 导出 + 脚本调度的轻量方案，暂不搭建 SpringBoot 服务 |
| **04** | 前端可视化开发效率低：定制化前端大屏开发周期长，难以快速交付 | 利用 Tableau / FineBI 等 BI 工具快速拖拽生成大屏，大幅减少前端代码开发量 |
| **05** | 项目整体工期与交付压力：需求范围过大，开发周期不足，无法按期完成所有功能 | 聚焦核心价值，砍掉流式入湖、实时指标等非核心模块，优先保障「批量湖仓构建 + 静态大屏展示」的基础交付闭环 |
