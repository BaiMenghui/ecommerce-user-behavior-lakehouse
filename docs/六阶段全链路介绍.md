# 电商用户行为湖仓分析平台 —— 阶段1~6 全链路介绍

> 本文档面向答辩与演示场景，系统介绍平台从原始数据到可视化大屏的六个阶段：每个阶段讲清楚"做什么、怎么做、产出什么、如何验证"，并给出可复现的核心指标基准。

---

## 一、平台概述

### 1.1 项目定位

本平台是一套围绕电商用户行为数据的**湖仓一体（Lakehouse）离线分析系统**，覆盖"数据清洗 → 数据入湖 → 数仓分层建模 → 指标计算 → 服务化接口 → 可视化大屏"的完整链路。全链路一键可重跑，每一层都有自动化校验，保证指标口径一致、结果可追溯。

### 1.2 技术栈

| 层次 | 技术选型 |
|---|---|
| 数据清洗 | Python 3 + pandas |
| 湖仓存储 | Apache Hudi 0.14.1（MOR / COW 表）on Spark 3.3 本地模式 |
| 数仓引擎 | Spark SQL（Hive Catalog + Derby 元数据） |
| 服务层 | Spring Boot（JDK 17）+ 多级缓存（Redis / Caffeine 自动降级） |
| 可视化 | Vue 3 + Vite + ECharts |

### 1.3 数据集

采用阿里巴巴天池淘宝用户行为数据集（UserBehavior）抽样，共 **1,048,576 条**原始记录，字段包括：用户ID（user_id）、商品ID（item_id）、商品类目ID（category_id）、行为类型（behavior_type：pv 浏览 / fav 收藏 / cart 加购 / buy 购买）、时间戳（ts）。

### 1.4 数据流总览

```
UserBehavior.csv（原始 104.9 万条）
   │  阶段1：pandas 清洗（8 步流水线）
   ▼
data/cleaned/dt=YYYY-MM-DD/（25 个日期分区）
   │  阶段2：Spark + Hudi 批量入湖（MOR 表）
   ▼
ods_user_behavior_log（ODS 贴源层）
   │  阶段3：维度建模 + 明细事实 + 汇总宽表
   ▼
dim_user / dim_item / dim_date（DIM 层）
dwd_user_behavior_fact（DWD 明细层）
dws_user / dws_item / dws_category（DWS 汇总层，COW）
   │  阶段4：指标聚合 + 交叉校验 + CSV 导出
   ▼
ads_dau_trend / ads_funnel / ads_item_topn / ads_category_share / ads_hour_heatmap
   │  阶段5：SpringBoot 服务化（REST API + 缓存）
   ▼
/api/kpi/summary、/api/funnel、/api/dau-trend …
   │  阶段6：Vue 大屏消费接口
   ▼
7 面板数据可视化大屏
```

## 二、阶段1：数据清洗与预处理

**脚本**：`scripts/stage1_data_clean.py`（pandas）
**输入**：`data/UserBehavior.csv`（1,048,576 条）
**输出**：`data/cleaned/dt=YYYY-MM-DD/user_behavior.csv`（25 个日期分区）+ 清洗报告

### 2.1 八步清洗流水线

1. **加载原始数据**：全量读入 CSV，打上数据总量基准。
2. **缺失值处理**：对关键字段做空值识别与剔除，保证主键与维度字段完整。
3. **去重**：按业务主键（用户+商品+行为+时间戳）删除完全重复记录。
4. **异常检测与过滤**：过滤行为类型不在 {pv, fav, cart, buy} 内的脏记录，以及逻辑异常数据。
5. **时间戳转换与标准化**：将 Unix 时间戳解析为 `event_time`（行为发生时间）与 `dt`（日期分区字段），统一为标准日期格式。
6. **按天分区落盘**：按 `dt` 拆分为日期分区目录，每天一个 CSV，为后续 Hive 风格分区表做准备。
7. **生成清洗报告**：输出 `cleaning_report.json` 与 `partition_summary.csv`，记录每个分区的行数与清洗统计，答辩时可直接展示数据血缘。
8. **自动校验**：分区总数、缺失值、重复值、行为类型四项核验。

### 2.2 本轮重跑结果

- 原始 1,048,576 条 → 清洗后 1,048,576 条（该抽样数据质量较高，无删除记录）
- 共 **25 个日期分区**，主体数据集中在 2017-11-24 ~ 2017-12-03
- 存在一个已知异常分区 `dt=2018-08-28`（仅 16 条，日期游离在主分析期 8 个月之外），清洗阶段按"忠实保留、下游闭环剔除"的策略处理
- 四项校验（记录数 / 缺失值 / 重复值 / 行为类型）全部 **PASS**

**答辩讲解点**：为什么用 pandas 而不是直接 Spark？——原始数据在单机内存可承载（约 100 万行），pandas 清洗秒级完成且便于生成细粒度清洗报告；规模化场景可无缝替换为 Spark DataForeg 清洗，分区落盘约定不变。

## 三、阶段2：ODS 贴源层批量入湖

**脚本**：`scripts/run_ods_ingestion.sh` + `sql/stage2_ods_ingestion.sql`
**输出**：Hudi MOR 表 `ods_user_behavior_log`

### 3.1 建表设计

通过 Spark SQL 创建 **Hudi MERGE_ON_READ 表**，关键参数：

- 主键 `behavior_id`（由 用户+商品+行为+时间戳 拼接生成，天然防重）
- 预合并字段 `preCombineField = ts`（同一主键以最新时间戳为准）
- 分区字段 `dt`（与清洗层日期分区对齐）
- 开启 HoodieCatalog 与 KryoSerializer，warehouse 目录统一管理湖仓文件

选择 MOR 表的原因：ODS 层写入频繁、后续可能存在更新场景，MOR 将合并代价转移到读侧异步 compaction，写吞吐更高。

### 3.2 入湖流程

重跑采用"**先清后灌**"策略：先 `DROP TABLE` 并删除 warehouse 中旧表目录，再执行建表 + 从 25 个清洗分区批量 INSERT 入湖，保证与上一轮结果零残留、口径一致。入湖完成后自动执行校验 SQL。

### 3.3 校验结果

- 分区数 25，总记录数 **1,048,576**，与清洗层逐分区一致
- 行为分布：pv 940,047（89.65%）/ cart 57,861（5.52%）/ fav 29,353（2.80%）/ buy 21,315（2.03%）
- 时间跨度 2017-09-11 ~ 2018-08-28 共 351 天，与清洗报告吻合
- 主键唯一性、空值检查通过

**答辩讲解点**：Hudi 相比裸 Parquet 的价值——时间线（Timeline）提供事务与回滚能力、upsert 支持数据订正、分区裁剪加速下游查询；`behavior_id` 作为主键让"重复入湖幂等"成为可能。

## 四、阶段3：数仓分层 DIM / DWD / DWS

**脚本**：`scripts/rerun_stage3.sh`（串行调度 6 个子任务）→ `stage3_dim_etl.py`、`stage3_dwd_etl.py`、`stage3_dws_etl.py`、`stage3_dws_check.py`

### 4.1 DIM 维度层（3 张维度表）

| 表 | 行数 | 关键内容 |
|---|---|---|
| dim_user | 20,404 | 用户代理键 user_key（UUID）、首次/最近活跃日期、活跃天数、生命周期分层（new / active / long_tail） |
| dim_item | 824,738 | 商品-类目归属、首次/最近被交互日期、各行为累计次数、商品生命周期分层 |
| dim_date | 25 | 日期维度（年/月/周几等属性），支撑按天对齐与时间轴补齐 |

维度表由 ODS 全量聚合构建，代理键采用 UUID 避免与业务主键耦合，为后续缓慢变化维（SCD）留出演进空间。

### 4.2 DWD 明细事实层

`dwd_user_behavior_fact`：一行一条行为明细，在 ODS 基础上补充 event_time 派生字段（小时、时段等），是所有汇总指标的**唯一明细事实来源**。本轮产出 1,048,576 条，与 ODS 总量守恒。

### 4.3 DWS 汇总宽表层（3 张 COW 表）

| 表 | 粒度 | 行数 | 主要指标 |
|---|---|---|---|
| dws_user_action_day | 用户 × 天 | 73,544 | 四类行为计数、会话质量、新老用户标记 |
| dws_item_action_day | 商品 × 天 | 711,458 | 四类行为计数、独立用户数（去重） |
| dws_category_action_day | 类目 × 天 | 32,326 | 四类行为计数、动销商品数、类目生命周期分层 |

DWS 采用 **COW（Copy on Write）表**：读多写少的汇总场景下，COW 读侧零合并开销，查询性能更稳。

### 4.4 三角核对（本阶段的质量闸门）

对每个分区执行"明细 == Σ用户宽表 == Σ商品宽表 == Σ类目宽表"的四口径互核，pv / fav / cart / buy 四种行为分别核对。本轮 25 个分区全部 **ALL PASS**，例如 dt=2017-11-25：明细 pv 99,250 = 用户宽表合计 = 商品宽表合计 = 类目宽表合计。

**答辩讲解点**：为什么 DWD 之上还要建 DWS？——把"用户/商品/类目 × 天"的重复聚合收敛到公共汇总层，ADS 层只做轻量再加工，多指标口径天然一致；三角核对则保证任何一层聚合都没有丢数或重算。

## 五、阶段4：ADS 指标层与结果导出

**脚本**：`scripts/rerun_stage4.sh` → `stage4_ads_etl.py`、`stage4_ads_check.py`、`export_ads_csv.py`
**输出**：5 张 ADS 应用层表 + 5 份 CSV

### 5.1 五张 ADS 表（与大屏面板一一对应）

| 表 | 服务的大屏面板 |
|---|---|
| ads_dau_trend | DAU·GMV 趋势折线 + KPI 数字卡（含新老占比、客单价） |
| ads_funnel | 浏览→收藏→加购→购买 转化漏斗 |
| ads_item_topn | 热销商品 Top10 排行榜（按购买次数降序） |
| ads_category_share | 类目销售占比饼图（Top15 + 其他聚合） |
| ads_hour_heatmap | 24 小时行为流量堆积柱状图（DWD 直通聚合） |

### 5.2 21 项多口径交叉校验

以 dt=2017-11-25 为基准日，将 ADS 指标与 DWD / DWS 逐项互核，全部 **PASS**：

- DAU 7,308（DWD == DWS == ADS，且 新用户 + 老用户 = DAU 守恒）
- 漏斗四行为：pv 99,250 / fav 2,921 / cart 6,010 / buy 2,043（三层一致）
- 订单量 2,043、GMV 556,190（复算 == ADS）
- TopN：行数 = min(10, 当日商品数)，降序排序与平分处理正确，Top1 购买次数 = 当日最大值 3
- 类目占比合计 ≈ 100%
- 热力图 Σaction 110,224 == DWD 当日明细行数，Σpv == 99,250

### 5.3 CSV 导出与异常分区闭环

`export_ads_csv.py` 将 5 张 ADS 表按 dt 升序导出为单文件 CSV（服务层直接消费），并内置**异常分区双保险过滤**：`dt=2018-08-28`（仅 16 条游离记录）不进入服务层口径。导出行数基准：24 / 24 / 154 / 32,317 / 284。

**答辩讲解点**：这是一段完整的数据质量闭环故事——原始数据携带 8 个月外的异常日 → 清洗层忠实保留可追溯 → ADS/服务层边界按"主分析期"口径剔除 → latestDt 日期口径恢复正确。体现了"分层治理、口径收敛"的设计思想。

## 六、阶段5：SpringBoot 服务层

**产物**：`springboot-service/target/lakehouse-api-1.0.0.jar`（JDK 17，端口 8080）

### 6.1 设计思路

服务层把 ADS 结果封装为 REST API，直接读取 `export/ads` 下的 5 份 CSV 并构建内存索引，实现"零外部依赖启动"（无需 Hadoop 集群即可演示）。多级缓存优先走 Redis，未部署时**自动降级 Caffeine 本地缓存**，健康检查中如实上报当前缓存类型。

### 6.2 接口清单（全部 200 验证通过）

| 接口 | 用途 | 冒烟结果（dt=2017-12-03） |
|---|---|---|
| /api/health | 健康检查（状态/缓存类型/数据目录/latestDt） | UP，latestDt=2017-12-03 |
| /api/dates | 可选日期列表（大屏日期选择器） | 24 个主分析期日期 |
| /api/kpi/summary | 当日 KPI 汇总 | DAU 9,522 / 订单 2,510 / GMV 695,041 / 客单价 402.46 / 付费用户 1,727 |
| /api/dau-trend | DAU·GMV 24 天趋势 | 主分析期逐日序列 |
| /api/funnel | 当日转化漏斗 | pv 113,054 / fav 3,555 / cart 7,072 / buy 2,510；加购率 6.26%、加购→购买 35.49%、浏览→购买 2.22% |
| /api/topn | 当日热销 Top10 | 按购买次数降序 |
| /api/category-share | 类目占比 | Top15 + 其他 |
| /api/hour-heatmap | 24 小时行为分布 | 按行为类型分列 |

统一响应结构 `{code, msg, data}`，异常路径统一错误码，便于前端处理。

## 七、阶段6：Vue 可视化大屏

**目录**：`vue-dashboard/`（Vue 3 + Vite + ECharts，开发端口 5173，代理直连服务层）

### 7.1 布局与面板

采用 **"4+2+1" 科技风深色大屏布局**（CSS Grid 分区）：

- **头部通栏**：平台标题、实时时钟、缓存类型徽标、服务状态灯（30 秒轮询 /api/health）、日期选择器
- **左侧 KPI 竖排**：DAU 活跃用户、新增/老用户、订单量、GMV 销售额、客单价——数字卡带副标题口径说明
- **中部两列**：DAU·GMV 双轴趋势折线（24 天）、转化漏斗、Top10 商品横向排行榜、类目销售占比环形图
- **底部两列**：24 小时行为流量堆积柱状图（按 pv/fav/cart/buy 着色）、用户行为分布环形图

### 7.2 交互逻辑

- 日期选择器切换 → 一次并发拉取 6 个接口，**全面板联动刷新**，带 loading 与错误横条兜底
- 默认选中日期列表末位（即主分析期最后一天 2017-12-03），打开即呈现最有数据的画面
- 服务异常时头部状态灯转红，数据面板保留最后一次成功结果

### 7.3 验收结论

浏览器实测：7 个面板全部正常渲染，KPI 显示 DAU 9,522 / 订单 2,510 / GMV ¥695,041 / 客单价 ¥402.46，与服务层冒烟值逐位一致；状态灯"服务正常"，日期 2017-12-03。

## 八、核心指标基准速查（答辩必备）

| 指标 | dt=2017-11-25 | dt=2017-12-03 |
|---|---|---|
| DAU | 7,308 | **9,522** |
| 浏览 pv | 99,250 | 113,054 |
| 收藏 fav | 2,921 | 3,555 |
| 加购 cart | 6,010 | 7,072 |
| 购买 buy | 2,043 | **2,510** |
| GMV | 556,190 | **695,041** |
| 客单价 | ≈272 | 402.46 |

**数据规模**：清洗/入湖 1,048,576 条 → dim_user 20,404 / dim_item 824,738 / dim_date 25 → DWD 1,048,576 → DWS 73,544 / 711,458 / 32,326 → ADS 5 表 24/24/154/32,317/284 → CSV → API → 大屏 7 面板。

**质量闸门**：阶段1 四项校验、阶段2 入湖逐分区校验、阶段3 分区级三角核对、阶段4 21 项多口径交叉校验、阶段5 接口冒烟、阶段6 大屏目测验收——六道闸门全 PASS，全链路指标同源同口径。
